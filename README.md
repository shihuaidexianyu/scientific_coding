# Scientific Coding

`scientific-coding` 是一个面向科研流水线的 AI 编程 skill。它希望交付的代码能够直接帮助研究者理解方法：最初有哪些数据，每一步为什么这样处理，数据结构和样本如何变化，最后的结果来自哪次配置与运行。

它同时约束 **agent 如何完成工作** 和 **生成的科研程序如何组织与运行**。前者采用分轮撰写、局部修正和核验；后者保持清晰的数据流，在执行入口统一保存运行记录。

适用于研究中的数据预处理、统计分析、推断、实验脚本和结果展示。已有项目沿用合适的配置、日志与调度机制；新项目默认采用带中文说明的 TOML。通用数值库、数据集 SDK、解析器和基础设施保留各自合适的工程结构。用户已确定的任务范围、科学选择和项目约定优先。

## 设计思路

### 让科学方法容易读懂

科学正确性、可读性和结果可追溯性决定代码结构。一个阶段围绕一个清楚的科学目的组织，主要计算按执行顺序展开，用有意义的中间变量表达数据变化。函数用于命名明确的科学操作或读写边界，重要计算应能直接定位。

生成代码不以节省 token、行数或字符数为目标。应完整写出具名中间结果、独立步骤和中文说明，不为缩短输出改成难读的语法糖、调用链或短路表达式。上下文紧张时按完整语义单元续接；精简 skill 的重复指令不放宽交付代码的可读性要求。

阶段之间通过有说明的数据连接；编排器负责调用顺序、路径和执行选择。统计量、区间、筛选和归一化等计算归入明确的分析步骤，展示代码使用已经计算的结果。不同科学方法的差异应在源码中可见。

### 让说明出现在阅读发生的位置

中文说明与代码放在一起：文件头解释整个文件，函数文档解释当前调用，代码块前的注释解释紧接着的操作，TOML 注释解释科学参数。读者应能沿源码理解处理过程，也能在函数调用处悬停查看参数和产物的具体结构。

注释按语义单元组织。一行独立完成一个操作时解释这一行；连续几行共同完成一件事时，用一段注释说明这几行。注释应说明目的、数据和重要变化，避免机械翻译语法。说明必须与真实实现一致；发现路径、单位或处理逻辑写错时，先修正错误说明，行为改动需有明确依据。

### 先写原始逻辑，再论证必要检查

初稿只表达读取、变换、计算和输出，不预装 assert、预检、防御分支、自动兜底或审批门控。科学方法本身的筛选与分支照常表达，正常 API 异常自然传播。

整体逻辑完成后，每项候选检查都要有具体、可信的触发依据，说明发生可能性、实际后果、已有保证、正常 API 为何不够，以及收益是否抵得上阅读和维护成本。没有依据就不加；未知概率不等于需要防御，极小概率的偶发内存错误不构成理由。

例如，statistics.mean 已明确拒绝空列表，通常不再加同义检查；某种估计至少需两个样本、但现有 API 仍会返回误导结果时，才针对真实筛选风险考虑保护。外部文件也不是自动必检理由。已有保证保持有效时直接复用；修改旧代码先评估各项保护，不一概删除。详见[检查的准入依据](scientific-coding/references/checks.md)。

作者的离线测试、科学设计核验和外层运行记录继续保留，它们不应变成程序内部的重复扫描、审批或检查管理框架。

### 连续完成研究，同时保留复核依据

输入与科学选择已经确定后，流水线默认连续运行。人工介入集中在尚未确定的重要科学选择，以及用户明确选定的查看位置。进入新阶段或生成中间文件，不自动产生审批关卡。

每次运行仍保留数据来源、有效配置、代码与环境、样本变化和运行日志。重跑使用新目录，旧结果与失败诊断保留。这样可以复核研究过程，也可以比较不同参数和不同尝试。

## 从任务到交付的工作流程

```text
用户的目标 / plan / 现有代码与数据
                |
                v
读取当前文件，确认数据、方法、范围和已有决定
                |
                v
实现 --> 简化 --> 中文说明 --> 自动格式
                                |
                                v
                            最终核验
                                |
              +-----------------+------------------+
              |                                    |
          发现具体问题                         相关问题已处理
              |                                    |
              v                                    v
    返回受影响的一轮，修正后复核       交付代码、结果、验证和运算成本估计
```

### 五轮各解决一个问题

| 轮次 | 主要工作 | 完成依据 |
|---|---|---|
| 实现 | 只写贯通输入、计算与输出的原始逻辑，不预装防御检查或门控 | 方法完整，计算和科学分支可以定位 |
| 简化与判断 | 整体完成后简化结构，论证实际候选检查的必要性 | 检查有可信触发依据和收益；不成立就不加 |
| 说明 | 补全中文文件头、函数文档、语义块注释、关联 TOML 和数据说明 | 当前调用的参数与产物结构在本地就能看懂，说明与实现一致 |
| 格式 | agent 编写并执行本次语言的临时脚本，落实注释空行与 80 字符行宽 | 最终文件检查通过，解析含义与字符串内容保持不变 |
| 核验 | 对照实际源码、配置、数据与结果，检查科学逻辑、可读性和说明真实性 | 相关测试及检查通过，具体问题已处理，未覆盖范围已说明 |

先简化再补全说明，可以减少为冗余代码撰写大量注释后的返工。实现阶段仍要留下科学理由，避免最后凭猜测补注释。可以为准确性和可读性投入更多 token，额外工作应解决具体的不确定性。

这些轮次是 agent 的工作方式。一个作者可以完成多轮；完整 plan 或跨多个函数的说明、简化任务，在环境支持并允许分工时，由另一个 agent 做最后的只读核验。核验者先读真实文件，再看作者的完成声明；发现问题后，由明确的编辑负责人局部修正。没有独立 agent 时，由当前 agent 重读最终文件并说明核验范围。

每次返工应对应具体问题：空行遗漏回到格式轮，单位写错回到说明轮，重复检查回到简化轮，科学行为错误回到实现轮。修改后复核受影响部分。小改动只做适用的工作，已经通过且仍有效的检查直接复用。

详细规则见[分轮工作与协作](scientific-coding/references/workflow.md)。

### 用户中途提问或修改代码

| 用户介入 | agent 如何衔接 |
|---|---|
| 询问代码含义、依据或进展 | 基于当前代码回答，然后继续原任务 |
| 新增或修正要求 | 更新受影响范围，保留仍适用的决定和已完成工作 |
| 手动修改代码或配置 | 编辑前重读当前文件，以用户修改后的版本为起点，更新相关说明与验证 |
| 明确暂停或更换目标 | 停止相应执行，保留成果和续接位置 |

例如，用户将保留条件从 `amplitude >= floor` 改为 `amplitude > floor`，agent 需要同步阈值注释、TOML 说明、边界测试、排除记录和受影响的统计结果。旧结果继续保留；旧测试只能说明旧版本。只有无法从上下文解决的实质冲突才需要澄清，其余工作继续推进。

## 生成的代码与数据应是什么样

### 三层中文说明

| 阅读位置 | 应看到的内容 |
|---|---|
| 文件开头 | 文件用途、字符流程图、输入与输出文件、加工逻辑、关联 TOML 和路径基准；包括同文件 `run/main` 的实际读写职责 |
| 函数调用处 | 简短用途，随后依次为“参数、返回、处理过程、副作用”；逐项解释类型、具体结构、轴、单位和必要约定 |
| 代码与配置旁 | 每个语义操作、TOML 配置节和键的就地说明，解释目的、参数含义和科学影响 |

Python 文件头的开引号 `"""` 独占一行，下一行写用途，再放字符流程图。函数使用函数体首条真正的 docstring，使语言服务能够在调用处提供说明。

每个参数和顶层返回成员的名称、类型单独一行，下面缩进解释，成员之间留空行。嵌套字典按字段展开；单个字段可以使用一条清楚的列表项。同型映射可以共享说明，但必须交代键、值类型和含义。当前返回结构要在当前函数文档中给出，不能仅写“见另一个函数”。源码、注释、docstring 和 TOML 每行最多 80 个字符，由任务脚本检查最终文件。

表达式和循环也有明确约束：推导式最多一层，额外的 `for`/`if` 嵌套展开为显式步骤；传参前给筛选、映射和复合构造的中间结果命名；复杂短路与多级 fallback 改成 `if`/`elif`/`else`。每个循环只承担一个职责，收集、判因和构造输出分成具名步骤。结构简化同时保留原有顺序、边界和惰性消费，不能只靠换行满足要求。

每个代码注释块前空一行，注释紧接它解释的代码；同一个连续注释块内部保持连贯。函数 docstring 后的第一个 `#` 注释块也适用。格式脚本需要识别真实注释，保护字符串、多行字符串和必要指令，并用故意缺空行等小例子验证自己。脚本在撰写时运行，不进入正常科研计算。

格式正确和内容准确分别核验。环境提供编辑器或语言服务时，应检查实际 hover，特别是嵌套字段的层级和分段；仅解析 docstring 不能证明实际显示效果。具体写法见[可读性规范](scientific-coding/references/readability.md)和[文件头与函数模板](scientific-coding/templates/stage_header.md)。

### 数据说明覆盖整个流水线

入口集中说明最初有哪些数据、来自哪里、文件格式是什么、如何读取。每个阶段产物再说明同类信息，以及相对输入发生了什么变化：

- 字段或数组轴、类型、形状、单位和科学含义。
- 样本 ID、顺序、对齐规则、缺失值及必要约定。
- 排除样本的逐 ID 原因，拆分或聚合的父子映射，参与计算的权重。
- 文件位置、实际路径基准、读取方法和下游用途。

重要的内存中间变量也在对应代码旁解释结构与变化，不因此强制增加落盘文件。未知的数据属性应明确标注。多输入连接还需说明各输入角色、关联键、连接基数和缺失匹配如何处理。详见[数据契约与来源](scientific-coding/references/artifact.md)。

## 科研程序如何运行和留痕

```text
创建新尝试，打开日志并记录 running
                  |
                  v
读取配置与输入 --> 阶段计算 --> 完整产物发布 --> 下游阶段 / 展示
                  |                |
                  +----------------+
                           |
                           v
             保存实际状态、耗时、资源和结果位置
                           |
                           v
                    更新本次实验索引
```

执行入口在业务代码启动、科学配置解析和数据读取之前建立记录。一个顶层尝试共用一份记录，内部阶段只补充进度和耗时；单独启动某个阶段时，才创建它自己的尝试。

| 记录 | 保存什么 |
|---|---|
| 来源与复现 | 实际输入角色和哈希/版本，有效配置及覆盖项，代码版本或含未提交修改的源码哈希，环境、依赖和随机信息；凭据不写入来源 |
| 样本变化 | 数量与单位、排除 ID/原因、拆分与聚合映射，必要的划分或置换身份 |
| 完整日志 | stdout、stderr、完整异常堆栈及子进程实际输出，可以合并为日志文件 |
| 执行状态 | 尝试编号、命令、工作目录、UTC 起止、实际退出码、最后进入和完成的阶段 |
| 时间与资源 | 整体墙钟时间、阶段时间、可获得的 CPU 时间和峰值 RAM，使用 GPU 时的 VRAM；注明统计范围和测量方式 |
| 批量索引 | 每次尝试的实验标识、配置、状态、时间、资源摘要、日志和结果位置；失败、取消和重试也保留条目 |

已有来源通过路径或绑定关联，避免在每个记录中重复复制与核验。资源无法采集时填写 `null` 并说明原因；采样峰值、进程寿命峰值和单阶段增量要区分。执行成功和科学结果是否显著也分别表示。

正常完成、失败、取消、启动失败和用户指定暂停应能区分。未确认结束的运行保留未知状态。失败日志、失败时实际读取的配置和可用来源仍需保存；清理未发布的临时载荷时，保留尝试目录中的诊断。

重跑始终使用新编号。完整科学产物先在暂存位置准备好，再发布到新目录；持续变化的日志和状态放在已封存产物之外。并行任务可以各写一份独立索引，避免竞争同一个追加文件。项目已有日志或调度机制时直接适配。详见[运行记录规范](scientific-coding/references/execution.md)。

## 代码交付后如何说明运算成本

完成科研代码或改变计算工作量的配置后，agent 需要给出中文运算时间与效率估计，包含以下依据：

1. **工作量**：主导成本的数据维度、文件大小、重复次数等。
2. **运行条件**：CPU/GPU、内存、worker/线程数和其他关键假设。
3. **成本模型**：主要时间与内存复杂度、可能的瓶颈，以及有依据的单次或批量耗时。
4. **证据与不确定性**：哪些是实际测量，哪些是外推，哪些尚未校准。

例如，逐次处理长度为 N 的输入，进行 B 次 bootstrap 并排序 B 个统计量，时间包含 `O(BN + B log B)`，还要考虑读取、启动和保存成本。批量耗时受实际并发数、争用和长尾影响，不能默认 worker 数增加几倍就快几倍。

没有数据规模、目标机器或校准依据时，明确说明无法可靠给出绝对耗时，仍提供复杂度与最小校准办法。纯注释和排版改动可以沿用仍有效的测量。

真正的性能优化另有证据要求：先测量代表性端到端工作量，定位瓶颈，再决定是否值得增加复杂度；修改后检验科学等价性，并在同一工作量上重新测量。详细要求见[成本估计与性能优化](scientific-coding/references/optimization.md)。

最终交付应让用户找到代码、配置、数据说明、结果、日志和索引，并看懂本次改动、实际验证范围及成本估计。报告长度随任务规模调整。

## 开始使用

将完整 `scientific-coding/` 目录放入 agent 能发现的技能目录。例如，在支持项目级技能的环境中，目录可以是 `.agents/skills/scientific-coding/`，其中保留 `SKILL.md` 和全部配套资源。随后显式调用：

```text
使用 $scientific-coding，按这个 plan 完成科研流水线。
先阅读现有代码和数据说明，保留已确定的方法与我的手动修改。
交付代码、相关验证、运行记录及运算时间和内存估计。
```

### 运行自带示例

Python 3.11+，科学计算仅依赖标准库。Windows 若已有 psutil，示例使用它获取峰值 RSS；不可用时记录原因。Linux/macOS 使用标准库 resource。

从仓库根目录执行：

```bash
python scientific-coding/examples/minimal_pipeline/pipeline.py
```

示例依次生成合成试次、筛选并记录排除原因、计算 bootstrap 区间，最后生成 SVG。其科学数据和参数用于演示方法组织。默认完整运行在示例目录内留下：

```text
artifacts/run_<结果编号>/
    raw_trials/                原始试次及契约、配置、来源
    processed_trials/          保留试次和排除记录
    analysis_result/           统计结果和聚合映射
    results.svg                最终展示
    results.provenance.json    图的来源
    pipeline_config.toml       编排配置副本

executions/attempts/<尝试编号>/
    run.log                    完整输出与异常
    execution.json             执行状态、时间及关联信息
    progress.json              阶段进度和资源
    snapshots/                 启动源码及实际读入的配置

executions/index/<尝试编号>.json
                               本次尝试的独立索引
```

`execution.json` 中的 `progress.result_path` 关联科学结果目录。复用外部输入时，记录已核验的输入绑定；对应上游生产目录会省略。失败或暂停时只保留已完成的部分，不能按完整运行目录清单判断成功。

初始数据、各产物结构、配置项、日志读取方式及用户选定暂停点的用法，见[示例 README](scientific-coding/examples/minimal_pipeline/README.md)。复制示例到独立目录时，通过 `SCIENTIFIC_CODING_SCRIPTS` 指定本 skill 的 scripts 绝对路径。

JSON 模板是结构参考，尚未采集的环境、时间和性能为 null，核验/优化结论为未评估；运行后据实填写。集成示例包含可选产物协议和暂停设施，普通任务不必整体复制，它的历史成绩也不代表满足后续新增的全部规范。

主入口只维护共同约束和阅读路由。完整版式集中在可读性与函数模板；普通成本估计不再加载完整优化流程，普通核验不再加载全部 linter 代码表。无需每轮重读全部参考，也不把测试夹具、历史报告和集成演示当作强制上下文。

需要哈希绑定产物时，可使用 `scientific_artifact.py`。`finalize` 封存契约、科学数据和来源，默认无需人工批准；完整目录的发布由 I/O 边界负责。`verify --full` 用于独立核对实际载荷。只有用户明确选定的评审点才涉及 `--request-review` 和相应决定；详见[产物规范](scientific-coding/references/artifact.md)。

## 验证方式与当前证据

静态检查核对依赖边界、配置和来源关系；科学测试核对数值、样本和行为；语言服务检查实际 hover；独立评读对照源码与说明。不同证据结合使用，格式器自报 clean、linter 通过或进程退出码为 0，都不能单独证明科学结果和注释准确。

从仓库根目录执行程序回归与检查：

```bash
python -m unittest discover -s scientific-coding/tests
python scientific-coding/scripts/scientific_code_lint.py .
```

检查具体项目可使用 `--changed-only`；检查提交范围可使用 `--base-ref origin/main`；独立产物审计可使用 `--full-artifact-checks`。静态 linter 不负责注释块空行，agent 仍需执行自己的临时格式脚本。

真实模型评测使用隔离项目，保存提示词、轨迹、生成产物和结果检查。例如：

```bash
python scientific-coding/evals/run_evals.py --backend claude --mode explicit --language zh --repetitions 3 --workers 12 --judge
```

`mock` 用于检查评测流程。`baseline` 仅移除项目级技能副本，未隔离全局技能；`claude` 表示 CLI 后端，实际模型由环境配置和轨迹确定。未知评审、执行无效和真实行为失败分别保存，不能用成功重试覆盖失败记录。

当前规则的模型遵循仍有实际缺口：此前重复生成中出现过错误说明、返回结构遗漏和格式器误报。程序回归通过不能证明 agent 总能完整执行这些要求。不同版本的证据分别保存在[注释与稳定性报告](scientific-coding/evals/reports/2026-09-05-docstring-layout.md)和[运行记录及成本实测报告](scientific-coding/evals/reports/2026-09-06-execution-records.md)。
