# 先完成原始逻辑，再论证必要检查

本文件统一规定运行时检查的准入；阶段、数据、统计、视图等参考都服从它。
“检查”包括额外 assert、预检、类型/形状/范围复核、防御分支、自动修复、
异常兜底和运行门控。作者阅读代码、验证科学设计和运行独立测试属于撰写工作，
不等于向科研程序插入检查。

## 初稿只表达方法

先贯通读取、变换、计算和输出，不写任何额外防御检查，也不预留
validate 开关、检查占位函数或以后才打开的门控。科学方法本身的筛选、
分组、缺失值处理规则和必要算法分支仍然属于原始逻辑。
普通解析器、文件读取与数值库自然产生的异常直接传播；不添加预检或
catch-and-continue 来包裹它们。

研究要求“一对一连接”是方法语义，选择实现该语义的 API 不等于额外
搭建校验层；但不能借命名为 load/prepare 把防御扫描藏进入口。
明确记录方法的输入假设，不把“要求如此”写成“已经验证如此”。

初稿是撰写顺序，不要求立即启动大规模计算或发布结果。完整逻辑写好后，
再作必要性判断、接入用户要求的运行记录并完成相关验证。
日志负责记录实际发生的执行，不承担逐步审批；直接复用已有外层机制。

## 每个候选检查都须说明为什么不得不加

只对实际考虑保留或添加的检查作以下判断，不遍历所有想象中的异常：

- **具体错误与触发依据。** 哪种本项目输入、操作或已知失败会触发？
  有历史故障、代表性数据、实际用户编辑或清楚的因果路径吗？
- **发生可能性。** 有记录时给频次和适用范围；只有可信场景时如实定性。
  没有依据就写未知，不编造百分比，也不因无法排除就加检查。
- **实际后果。** 会静默改变科学结果、混淆样本，还是仅产生本来就明确的异常？
  不能只说“更安全”“更稳健”。
- **是否已经解决。** 当前构造、适用 API 契约、上游实际操作或正常异常
  是否已排除/暴露这个问题？中间哪一步可能再次破坏保证？
- **检查是否值得。** 它能有效发现具体问题吗？为何现有 API 报错、离线
  测试或更清楚的方法实现不够？收益是否抵得上阅读、维护和运行开销？

不能成立就不加，不要求凑出至少一项检查。概率与后果共同判断，
不设置脱离任务的固定概率门槛。理论上后果严重并不能代替可信触发依据。
无需为每项建立表格、概率模型、证明文件或用户审批；仅在不直观时，
用一句中文解释保留原因及它所保护的实际科学前提。

## 判断实例

| 候选情况 | 处理 |
|---|---|
| 普通路径不存在，open 已报告具体路径 | 直接读取，通常不再 exists 预检 |
| 内部构造生成唯一 ID，下游仅过滤且不改 ID | 不再查唯一性，不增加“已验证”标志 |
| statistics.mean 对空输入已有明确异常 | 自然传播，不另加同义空列表检查 |
| 某种估计至少需两个独立样本，而 API 接受一个仍返回误导结果；当前筛选确实可能剩一个 | 完整逻辑后论证这一科学前提，在受影响位置检查一次 |
| 两张外部表来自不同导出流程，重复键会让当前连接静默扩充样本 | 核对真实连接语义及 API 能力；有此风险且尚未解决时才补必要约束 |
| 程序刚产生的张量可能被极小概率内存偶发错误改变 | 不为这种假设增加逐层 shape、finite、checksum 或重复计算 |
| 复用另一运行的缓存，可能拿到旧配置/版本结果 | 先确认实际复用协议及身份绑定需求；使用已有必要核验，不另造全套扫描 |

“外部来源”“函数调用”“产生新文件”只是定位数据流的信息，不能单独证明
需要检查。哈希用于记录实际来源，不代表每个消费者都应重新散列并比较。
选择了按哈希验证精确身份的复用协议后，履行该协议一次即可。

## 改已有代码与最终核验

不要先把已有检查全部删除再重建。先读其保护的各个事实，逐项应用上述依据。
合并的 if 可能同时保护多个事实；相同 ID 集合不证明任一表自身没有重复，
删重复检查时不能顺手删掉唯一剩下的必要保护。

必要检查放在问题首次可能发生、且仍能避免具体后果的位置。普通函数边界
不制造新风险；变换后只考虑新受到影响的前提。不增加验证管理器、状态标志、
证明日志或每阶段记录器来管理这些保证。

最终作者检查科学结果、注释真实性和相关边界行为。用针对性反例验证仍需
保护的事实，用科学 oracle 验证改写没有改变方法；这些是离线验证，
不能自动转成正常运行时反复执行的检查。没有新疑点时停止重复核验。
